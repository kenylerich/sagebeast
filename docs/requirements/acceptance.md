# 怎样接受需求

聊天里的同意不会打开编码门禁。接受必须落在仓库里，才能被以后的 PR 和代理读到。

## 接受记录

维护者新增 `docs/decisions/0003-catalog-accepted.md`。文件至少包含：

- 日期。
- 接受的需求编号。未列出的编号仍然是草案。
- 已关闭的开放问题编号，并链接对应决策记录。
- 明确仍不接受的编号。
- 一句范围声明：只允许实现已列出的编号。

示例结构：

```markdown
# 0003. 接受的需求

日期：YYYY-MM-DD

接受：REQ-001、REQ-003

仍不接受：REQ-002、REQ-004、REQ-005、REQ-006、REQ-007、REQ-008

已决问题：无

范围：只实现已列出的编号。Q1 和 Q3 未决时，REQ-003 只能写契约测试，不能选择装载方式。
```

这只是格式示例，不是已经做出的接受。不要把示例复制成正式文件，除非维护者确认其中的编号。

## 建议的跟踪 Issue

文档推送后，开一条 Task：

- 标题：`接受需求目录`
- 标签：`track/requirement`、`status/inbox`、`area/process`、`area/docs`、`p0`、`source/maintainer`
- 正文链接本文件、[目录](catalog.md) 和 [开放问题](open-questions.md)。
- 完成条件是 `0003` 落地，或维护者明确要求继续只改文档。

在那条 Issue 被解决前，产品代码 PR 没有可引用的已接受需求。

## 部分接受

逐条接受是默认建议。只接受 REQ-001 不会允许创建插件或数据客户端。只接受 REQ-003 也不会允许在 Q3 未决时选择 MCP 或 Open API 作为唯一实现。

## 撤回

从 `0003` 删除一个编号即撤回开工许可。已经打开的实现 PR 要改成只保留文档，或关闭。不要把撤回前的提交继续堆功能。
